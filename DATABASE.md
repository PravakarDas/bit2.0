## ORM & Conventions

- **ORM**: Prisma 6.2.1 (`@prisma/client` + `prisma` CLI), provider `postgresql`, client generator `prisma-client-js`.
- **IDs**: every model uses `id String @id @default(cuid())` except three deliberate singleton config tables that hardcode `id: "global"` (`SystemSettings`, `SystemControlSettings`, `EmailConfig`).
- **Timestamps**: almost every model has `createdAt DateTime @default(now())`; most mutable models also have `updatedAt DateTime @updatedAt`. A few append-only/log-style models omit `updatedAt` (e.g. `WalletTransaction`, `Payment`, `AuditLog`, `SystemAudit`, `LeaveAuditLog`, `TimelineModificationActionLog`, `SystemControlChangeLog`).
- **Soft delete**: only `EmployeeNote` has a `deletedAt DateTime?` column; every other model is either hard-deleted or toggled via an `isActive`/`isArchived` boolean.
- **No `@@map` renaming** except `PublicHoliday` → `@@map("public_holidays")`. All other Prisma model names map 1:1 to their (PascalCase) Postgres table names.
- **Money is stored as `Float`**, not `Decimal` — see [DECISIONS.md](DECISIONS.md) for the implication (potential floating-point rounding, no schema-level fix observed).
- **Durations are stored as strings** (`"HH:MM"` or `"-HH:MM"`), not intervals/integers — e.g. `DailyTimeRecord.actualActiveTime`, `overtimeUndertime`. Parsed/formatted via `src/lib/duration.ts` at the application layer.

## Core: Users & Organization

### `User` (the central entity — 40+ columns)

Primary business entity. Key fields grouped:

| Group | Fields |
|---|---|
| Identity/auth | `id`, `clerkId` (unique), `email` (unique), `firstName`, `lastName`, `imageUrl` |
| Access | `role` (`Role`, default `EMPLOYEE`), `isManager` (Boolean, default `false`), `status` (`UserStatus`, default `PENDING`) |
| Lifecycle | `employeeStatus` (`EmployeeStatus?`, default `ACTIVE`), `isArchived`, `archivedAt`, `payrollContinuationMonths` (default `2`) |
| Money | `walletBalance` (Float, default 0), `baseSalary` (Float, default 0 — cached current salary; source of truth is `BaseSalary` history) |
| Org placement | `branchId → Branch`, `departmentId → Department`, `designationId → Designation` |
| Personal info | `gender`, `dateOfBirth`, `bloodGroup`, `nidNumber`, `phoneNumber`, `personalEmail`, current/permanent address fields (5 each) |
| Employment | `dateOfJoining`, `attendanceId`, `workingDaysInMonth` (default 22) |
| Emergency contact | 6 fields (`emergencyContact*`) |
| Nominee | 6 fields (`nominee*`) |
| Banking | `bankAccountNumber` |
| Professional links | `portfolioLink`, `githubLink`, `linkedinLink`, `fiverrLink`, `upworkLink` |
| Document links | `loanPapersLink`, `nomineesPapersLink`, `emergencyContactLink`, `personalInfoLink` |

**Relations (1:N unless noted):** `loans`, `medicalClaims`, `medicalEntitlements`, `salaryPayments`, `salaryHistory` (`BaseSalary`), `walletTransactions`, `walletRequests`, `leaveEntitlements`, `leaveApplications`, `timeRecords` (`DailyTimeRecord`), `temporaryTimeRecords` (`DailyTimeRecordTemporary`), `overtimePayouts`, `overtimeRequests`, `timelineModificationRequests` (as requester), `timelineModificationReviewed` (as reviewer), `timelineModificationActionLogs` (as actor and as target — two named relations), `profileUpdateRequests`, `loansVerifiedByManager`, `overtimeRequestsVerifiedByManager`, `employeeNotifications`, `sentBreakingNotices`, `targetedBreakingNotices`, `breakingNoticeRecipients`, `auditLogs` (`LeaveAuditLog`), `employeeAllowances`, `payrollOverrides`, `notesReceived`/`notesCreated` (`EmployeeNote`, two named relations).

### `Branch`

`id`, `name`, `location`, `isActive`, `isLoanApplicationEnabled` (per-branch loan toggle) · Timeline defaults: `checkInTime`/`checkOutTime` (`"HH:MM"`, default `09:00`/`18:00`), `breakDuration` (default `01:00`), `weeklyOffDays` (`String[]`, default `["SUNDAY"]`). Relations: `users[]`, `bonuses[]` (`BonusType`, implicit m:n), `targetedBreakingNotices[]`.

### `Department`

Self-referencing hierarchy: `parentId → Department` (relation `"DepartmentHierarchy"`, `onDelete: Restrict`), `children Department[]`. `name` unique. Relations: `designations[]`, `users[]`.

### `Designation`

Belongs to one `Department` (`onDelete: Restrict`). `@@unique([name, departmentId])` — same title can exist in different departments.

### `PublicHoliday`

`name`, `date`, `description?`, `isRecurring`, `appliesToAllBranches` (default `true`), `applicableBranchIds` (`String[]`) — branch scoping is an array of IDs rather than a join table. `isActive`. Maps to Postgres table `public_holidays`.

## Compensation: Salary, Allowances, Bonuses

### `BaseSalary`

Append-style history: `amount`, `effectiveFrom` (default now), `effectiveTo?`, `reason` (`SalaryChangeReason`, default `JOINING`). Belongs to `User`. `salary.actions.ts`'s `updateEmployeeSalary` closes the previous open record (`effectiveTo = effectiveFrom` of the new one) and creates a new one in the same transaction that also updates `User.baseSalary` — **two sources of the "current" salary that must stay in sync** (see [DECISIONS.md](DECISIONS.md)).

### `SystemSettings`

Singleton (`id: "global"`). `medicalClaimLimit` (Float, default 500).

### `AllowanceType`

`name`, `amount`, `valueType` (`FIXED`/`PERCENTAGE`), `scope` (`AllowanceScope`), `targetBranchIds` (`String[]`, only meaningful for `FULL_BRANCH` scope), `isActive`. Relations: `employeeAllowances[]`, `payrollOverrides[]`.

### `EmployeeAllowance`

Join table: `userId` + `allowanceId`, `isActive`. `@@unique([userId, allowanceId])`. `onDelete: Cascade` on both FKs.

### `PayrollAllowanceOverride`

Per-payroll-run, per-employee, per-allowance override: `payrollMonth` (e.g. `"2024-01"`), `isIncluded` (Boolean), `customAmount?`. `@@unique([payrollMonth, userId, allowanceId])`. `onDelete: Cascade` on both FKs.

### `BonusType`

`name`, `value`, `type` (`ValueType`), `isActive`. `branches[]` — implicit many-to-many with `Branch` (empty = applies to all branches, per `bonus.actions.ts`).

## Loans & EMI

### `Loan`

`issuedAmount`, `remainingPrincipal`, `gracePeriodMonths`, `totalMonths`, `status` (`LoanStatus`, default `PENDING`), `isManuallySeeded` (default `false`), `reason` (default `"Personal"`), `emiStartMonth?`/`emiStartYear?`, `approvedBy?`, `adminComments?`, `declineReason?`, `declinedBy?`. Manager-verification fields: `managerVerifiedAt?`, `managerVerifiedById → User` (relation `"LoanManagerVerification"`), `managerRejectionReason?`, `managerComments?`. Admin-decline-after-verification fields: `adminDeclinedReason?`, `adminDeclinedAt?`. Relations: `user → User`, `emiState EmiState?` (1:1), `payments Payment[]`, `auditLogs AuditLog[]`.

### `EmiState`

1:1 with `Loan` (`loanId @unique`). `currentEmi`, `carryForward` (default 0, absorbs rounding/negative-principal edge cases per `loan.service.ts`).

### `Payment`

`amount`, `type` (`PaymentType`), `payrollMonth`. Belongs to `Loan`.

## Wallet

### `WalletTransaction`

Append-only ledger row: `amount`, `type` (`TransactionType`), `description`, belongs to `User`. No `updatedAt` (immutable). The `description` string is used as a tag for idempotent reconciliation lookups elsewhere in the codebase (e.g. late-penalty diffing in `leave-automation.actions.ts`) — **treat `description` format changes as a breaking change** for that reconciliation logic.

### `WalletRequest`

Employee-submitted reimbursement request: `amount`, `description`, `status` (`WalletRequestStatus`), `attachmentUrl?`. Belongs to `User`.

## Medical

### `MedicalEntitlement`

Per-user, per-year: `totalLimit`, `remainingBalance`. `@@unique([userId, year])`. Relations: `user`, `claims[]`.

### `MedicalClaim`

`amount`, `description`, `attachmentUrl?`, `status` (`ClaimStatus`, default `PENDING`). Belongs to `User` and optionally `MedicalEntitlement`.

## Payroll

### `SalaryPayment`

One immutable row per user per month: `month` (`"YYYY-MM"`), `baseSalary`, `totalBonuses`, `totalAllowances`, `medicalReimbursement`, `loanDeduction`, `walletAdjustment` (default 0), `netAmount`. No `updatedAt` — payroll runs are not editable in place (see `payroll.actions.ts`'s immutability check).

## Leave Management

### `LeaveType`

`name` (unique), `allocatedDays` (per year), `requiresApproval` (default `true`), `isActive`, `leaveResetPolicy` (`LeaveResetPolicy`, default `ROSTER_EVERY_YEAR`), `applicableBranches` (`String`, default `"[]"` — **a JSON string, not a Postgres array**, unlike `PublicHoliday.applicableBranchIds`; inconsistent representation of the same "which branches" concept across two models — see [DECISIONS.md](DECISIONS.md)). Relations: `userEntitlements[]`, `leaveApplications[]`, `leaveAuditLogs[]`.

### `UserLeaveEntitlement`

Per-user, per-leave-type, per-year: `allocatedDays`, `usedDays` (default 0). `@@unique([userId, leaveTypeId, year])`.

### `LeaveApplication`

`leaveDate`, `reason?`, `status` (`LeaveApplicationStatus`, default `PENDING`), `approvedBy?` (string, admin/manager/"SYSTEM"), `approvedAt?`. Belongs to `User` and `LeaveType`.

## Attendance / Timeline

### `DailyTimeRecord`

The largest attendance model — one row per user per date (`@@unique([userId, date])`):

| Group | Fields |
|---|---|
| Status | `status` (`DailyRecordStatus`, default `PRESENT`) |
| Required (from branch settings or override) | `requiredCheckIn?`, `requiredCheckOut?`, `requiredBreakTime?` |
| Actual (from ZKTeco or manual entry) | `actualCheckIn?`, `actualCheckOut?`, `actualBreakTime?` |
| Computed | `requiredActiveTime?`, `actualActiveTime?`, `officialOvertimeundertime?` (office-only OT/UT), `requestedOvertime?` (from an approved `OvertimeRequest`), `requestedOTstart?`/`requestedOTend?`, `overtimeUndertime?` (official + requested combined) |
| Late-checkin | `lateCheckInMinutes?` (default 0), `lateCheckInPenalty?` (default 0, Float) |
| Auto-processing | `autoDeductedLeaveType?`, `isProcessed` (default `false`) |

All duration fields are `String?` in `"HH:MM"`/`"-HH:MM"` format, not a numeric/interval type — see [ORM & Conventions](#orm--conventions).

### `DailyTimeRecordTemporary`

Structurally identical to `DailyTimeRecord` (same field list) but `onDelete: Cascade` on the `User` FK and no unique-per-date constraint beyond `@@unique([userId, date])`. Used as a soft-archive destination when records are moved out of the live table (e.g. `profile.actions.ts` archiving pre-date-of-joining rows when an employee's join date changes, or `timeline.actions.ts` restoring previously-archived rows during backfill).

## Overtime

### `OvertimeRequest`

Employee-submitted: `overtimeDate`, `totalOvertime` (`"HH:MM"`), `requestedOTstart?`/`requestedOTend?`, `reason`, `taskNo?`, `status` (`OvertimeRequestStatus`, default `PENDING`), `reviewedBy?`/`reviewedAt?`/`declineReason?`. Manager-verification fields mirror `Loan`: `managerVerifiedAt?`, `managerVerifiedById → User` (relation `"OvertimeRequestManagerVerification"`), `managerRejectionReason?`, `managerComments?`, plus `adminDeclinedReason?`/`adminDeclinedAt?`. `requestedAt` (default now), `statusUpdatedAt` (`@updatedAt`).

### `OvertimePayout`

One row per user per year (`@@unique([userId, year])`): `baseSalary` (snapshot), `totalRequiredActiveTime`/`totalRequiredBreakTime`/`totalOvertimeUndertime` (string durations), `totalRequiredMinutes`/`totalOvertimeMinutes` (Int), `calculatedAmount` (Int), `isPaid` (default `false`), `paidAt?`, `paidBy?`.

## Notifications & Breaking Notices

### `AdminNotification`

`type` (`NotificationType`), `title`, `message`, `status` (`NotificationStatus`, default `UNREAD`), `metadata` (`Json?`). No FK to `User` — recipient is implicitly "all admins," and per-notification actor/target data (if any) lives inside `metadata`.

### `EmployeeNotification`

Per-user (`userId → User`): `type` (plain `String`, not an enum — e.g. `"AUTO_LEAVE_DEDUCTION"`), `title`, `message`, `relatedDate?`, `relatedEntityId?`, `isRead` (default `false`).

### `BreakingNotice` / `BreakingNoticeRecipient`

`BreakingNotice`: `title`, `targetType` (`BreakingNoticeTargetType`), `senderId → User`, optional `targetUserId → User` / `targetBranchId → Branch`, `version` (default 1), `isEdited`. Indexed on `targetType`, `senderId`, `targetUserId`, `targetBranchId`.
`BreakingNoticeRecipient`: per-recipient fan-out row — `noticeId`, `userId`, `status` (Boolean, seen flag), `seenAt?`, `visibleUntil?`, `noticeVersion` (default 1, used to detect stale/edited notices — see [ARCHITECTURE.md](ARCHITECTURE.md)). `@@unique([noticeId, userId])`, indexed on `[userId, status, visibleUntil]`.

### `ProfileUpdateRequest`

`userId → User`, `status` (`ProfileUpdateStatus`, default `PENDING`), `requestedChanges` (`Json`, only the changed fields), `previousValues` (`Json?`), `reviewedBy?` (Clerk ID string), `reviewedAt?`, `reviewNotes?`.

## Audit & System

### `AuditLog`

General-purpose: `oldEmi?`/`newEmi?` (despite the name, reused for non-EMI audit entries too — e.g. manager org-config changes set both to `null` and just use `changeReason`), `changeReason`, optional `loanId → Loan`, optional `userId` (plain string, **no FK relation defined** to `User`).

### `LeaveAuditLog`

Leave-automation-specific: `userId → User`, `action`, `description`, `affectedDate`, optional `leaveTypeId → LeaveType`, `previousBalance?`/`newBalance?`/`deductedDays?` (Int), `processedAt` (default now), `processingSource` (default `"SYSTEM"`), `metadata` (`Json?`).

### `SystemAudit`

Generic app-level event log (currently used by `email.service.ts` for send attempts and `payroll.actions.ts` for run outcomes): `action`, `details`, `status` (default `"SUCCESS"`).

### `SystemControlSettings` / `SystemControlChangeLog`

`SystemControlSettings`: singleton (`id: "global"`), holds `appTimezone`, timeline/ZKTeco/leave-automation cron enable flags + hour/minute (+ ZKTeco interval-mode fields), `zktecoBaseUrl`/`zktecoUsername`/`zktecoPassword` (**plaintext columns** — not encrypted, unlike `EmailConfig.appPasswordEncrypted`; see [DECISIONS.md](DECISIONS.md)), and `updatedById`/`updatedByEmail`/`updatedByRole` (denormalized actor snapshot, no FK).
`SystemControlChangeLog`: append-only diff log — `actorId`/`actorName`/`actorEmail?`/`actorRole`/`actorIsManager`, `changedFields` (`String[]`), `previousValues`/`newValues` (`Json?`).

### `EmailConfig`

Singleton (`id: "global"`). `provider` (default `"GMAIL"`), `smtpHost`/`smtpPort`/`secure`, `senderEmail`, `appPasswordEncrypted` (AES-256-GCM ciphertext, see `src/lib/crypto.ts`), `updatedById`/`updatedByEmail`/`updatedByRole` (denormalized, no FK).

### `EmployeeNote`

`employeeId → User` (`onDelete: Cascade`), `note` (free text), `createdBy → User` (relation `"EmployeeNoteCreator"`, `onDelete: Restrict`), `deletedAt?` (the only soft-delete model in the schema). Indexed on `employeeId`, `createdBy`.

### `TimelineModificationRequest` / `TimelineModificationActionLog`

`TimelineModificationRequest`: `userId → User` (relation `"TimelineModificationRequester"`), `requestedDate`, `requestedCheckIn?`/`requestedCheckOut?`/`requestedBreakTime?`, `reason?`, `status` (`TimelineModificationRequestStatus`), `reviewedById → User?` (relation `"TimelineModificationReviewer"`), `reviewerNote?`, `reviewedAt?`, `appliedAt?`. Indexed on `[userId, requestedDate]` and `status`.
`TimelineModificationActionLog`: `actionType`/`actionDetails`/`metadata (Json?)`, `actorId → User` (relation `"TimelineModificationActionActor"`), `targetUserId → User` (relation `"TimelineModificationActionTarget"`), optional `requestId → TimelineModificationRequest`, optional `dailyTimeRecordId` (plain string, **no FK**). Indexed on `[actorId, createdAt]`, `[targetUserId, createdAt]`, `requestId`.

## Relationship Summary

`User` is the hub almost every model connects to, directly or indirectly. Notable non-obvious relationships:
- `Loan.managerVerifiedById → User` and `OvertimeRequest.managerVerifiedById → User` are separate named relations from the primary `Loan.userId`/`OvertimeRequest.userId` — a loan/request has both an owner and (optionally) a verifying manager, both FKs to `User`.
- `TimelineModificationActionLog` has **two** FKs to `User` (`actorId`, `targetUserId`) plus an optional FK to its own parent `TimelineModificationRequest` — modeling "who did what to whom," not just a simple audit row.
- `EmployeeNote` has two FKs to `User` (`employeeId` — the subject, `createdBy` — the author) with **different `onDelete` behaviors** (`Cascade` vs `Restrict`): deleting the subject employee deletes their notes, but deleting the author is blocked while their authored notes exist.
- `AuditLog.userId` and `TimelineModificationActionLog.dailyTimeRecordId` are **plain strings with no Prisma relation** — these are "soft" references not enforced at the database level; do not assume referential integrity for these two fields.
- `Department` is self-referencing (`parentId`/`children`) with `onDelete: Restrict`, so a department cannot be deleted while it has children (`department.actions.ts` also blocks deletion at the application level if it has any users/designations).

## Migration Strategy

- 45 timestamped migrations under `prisma/migrations/`, from `20260124161942_init` (the initial schema) through `20260613000000_add_zkteco_sync_mode` (most recent as of this documentation). All directory names encode either a real Prisma-generated timestamp or a manually-authored date-like prefix (several later migrations use `0000` for the time portion, e.g. `20260316000000_...`, suggesting they were authored by hand rather than via `prisma migrate dev`'s auto-timestamping — a pattern worth preserving consciously rather than assuming every migration was tool-generated).
- Prisma's standard flow applies: `prisma migrate dev` in development (generates + applies + regenerates the client), `prisma migrate deploy` in production (applies only, no shadow database, safe for CI/CD — this is exactly what `Dockerfile`'s container start command runs).
- `prisma/migrations/migration_lock.toml` pins the provider to `postgresql` — do not switch providers without a full migration reset.
- **No `prisma db push` usage was found in any script** — the project consistently uses versioned migrations. Per project history (`[[feedback-prisma-db-push-safety]]`), `db push`/`migrate reset` must never be run against the real database without first diffing the live schema — a prior incident of this kind deleted real data on this project.
- `user.actions.ts` contains a defensive **self-healing migration workaround**: if a Prisma query fails with error code `P2022` (column does not exist) specifically for `User.fiverrLink`/`User.upworkLink`, it runs `ALTER TABLE "User" ADD COLUMN IF NOT EXISTS ...` directly via `$executeRawUnsafe` and retries. This indicates that at some point a production database was out of sync with a migration for these two columns — a symptom, not a recommended general pattern (see [TROUBLESHOOTING.md](TROUBLESHOOTING.md)).
- `branch.actions.ts` similarly has a runtime guard (`isMissingLoanToggleColumnError`) that falls back to `isLoanApplicationEnabled: true` if that column is missing, rather than auto-repairing — a softer version of the same defensive pattern.

## Seed Data

`prisma/seed.js` (run via `pnpm prisma db seed`, wired through `package.json`'s `"prisma": { "seed": "node prisma/seed.js" }`):
- Finds the **first** `User` row in the database (fails gracefully with a log message if none exists — expects you to have signed in at least once first).
- Creates two `PENDING` `Loan` records for that user (৳50,000 / 6-month grace / 12 months, and ৳120,000 / 3-month grace / 24 months) for manual testing of the loan approval flow.
- This is a minimal developer-convenience seed, not a full fixture set — "Not found in current project": seed data for branches, departments, leave types, or any other reference data (these must be created manually through the admin UI on a fresh database).

## Common Query Patterns

Representative patterns actually used in `src/actions/*.ts` (see [CLAUDE.md](CLAUDE.md#database-access-patterns) for when to use each):

```ts
// Standard read with relation include
prisma.user.findMany({
  where: { status: "APPROVED", isArchived: false },
  include: { branch: { select: { id: true, name: true } } },
  orderBy: [{ firstName: "asc" }, { lastName: "asc" }],
});

// Transactional multi-write (loan approval, payroll, leave approval, etc.)
prisma.$transaction(async (tx) => {
  await tx.loan.update({ where: { id: loanId }, data: { status: "ACTIVE" } });
  await tx.emiState.create({ data: { loanId, currentEmi, carryForward: 0 } });
  await tx.walletTransaction.create({ data: { userId, amount, type: "LOAN_DEDUCTION", description: "..." } });
});

// Singleton config upsert (SystemControlSettings, EmailConfig, SystemSettings)
prisma.systemControlSettings.upsert({
  where: { id: "global" },
  update: {},
  create: { id: "global", ...envDefaults },
});

// Raw SQL for a report that's awkward in the query builder (dashboard.actions.ts only)
prisma.$queryRaw(Prisma.sql`SELECT ... FROM "MedicalClaim" ... ${branchFilter}`);
```
